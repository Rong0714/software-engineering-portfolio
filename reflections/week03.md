# Task 1

Requirement and Documentation will have to change and signed off, testing and go-live will have to be pushed back due to new
implentation.

If the team were working in 2-week increments, the new multi-restaurant ordering feature could be added to the backlog and prioritised for a future increment. The team would estimate the work, make the necessary design and development changes, and test the feature within the increment. To keep the six-month deadline, a lower-priority feature could be delayed or removed. Overall, the change would be easier to manage than in the waterfall approach because the team can adjust priorities and scope throughout the project.

Waterfall: The change would be more expensive and time-consuming because requirements and design have already been completed. The team may need to redo parts of the design, change existing code, and potentially repeat testing. This could also cause delays to the project.

2-week increments: The change would generally require less additional cost and effort because it can be added to the backlog and planned into a future increment. However, it still requires development and testing effort, and another feature may need to be delayed.


# Task 2

**Weakness:** Requirements are only communicated verbally.

**Issue:** Mainly the absence of any process. Even a lightweight Agile process should have clear, shared requirements such as user stories and acceptance criteria. Agile does not mean having no documentation. 

**Improvement:** Write a short user story and acceptance criteria for each feature before development begins.

**Priority:** MUST


**Weakness:** Code is pushed directly to the main branch

**Issue:** This is also largely the absence of a basic development process. A lightweight Agile process can include simple peer review without requiring heavy documentation or bureaucracy.

**Improvement:** Require one other developer to review and approve changes before they are merged.

**Priority:** SHOULD


**Weakness:** Testing is done only by the developer who wrote the feature

**Issue:** Disciplined lightweight Agile process could catch and prevent through acceptance criteria, peer testing and continuous testing. It does not require a heavyweight testing process.

**Improvement:** Use a short checklist of acceptance criteria and have another team member test the feature before release.

**Priority:** SHOULD
